# Implementation Plan: Hybrid Detection + Segmentation Diagram Recognizer

Reimplementation of Costa & Mello, "Hybrid Object Detection and Semantic Segmentation for
Offline Handwritten Diagram Understanding" (IEEE Access, vol. 14, 2026).

## Context

Goal: turn a photo or scan of a hand-drawn flowchart into a directed graph, then into
runnable Python. Follow the paper closely: train on a cloud GPU (Colab/Kaggle T4) and run
inference locally on CPU.

Decisions:
- Training runs on Colab/Kaggle. This machine has no GPU (torch 2.9.1+cpu).
- Detector is YOLOv7, as in the paper. Swapping in Ultralytics YOLO11 later stays a
  one-module change (`hdr/detect.py`).
- Full scope: detection, segmentation, OCR, graph, code generation, evaluation.
- Fully local models. No VLM in the pipeline.

Assets already in place:
- `handwritten-diagram-datasets/datasets/{fca,fcb,fa}`: COCO JSON plus PNG files.
- Arrow annotations carry `keypoints` (2 points), `waypoints` (polyline, FC_A/FC_B only),
  `arrow_prev`, and `arrow_next`.
- Text annotations carry a `text` string.
- Splits: FC_A has train 248 / test 171 and no val (use FC_B val, as in the paper).
  FC_B has 280/196/196. FA has 132/84/84.

## Project layout

```
diagram_generator/

    data/

    segment.py         # DeepLabv3 inference -> arrow mask

    pipeline.py        # image -> graph JSON + .py

```

## Steps

### Step 0: Environment
- Local: create `.venv` and install `torch` (CPU), `torchvision`, `transformers`,
  `opencv-python`, `scikit-image` (Zhang-Suen skeleton), `pycocotools`, `jiwer`,
  `numpy`, `pytest`.
- Colab: clone `WongKinYiu/yolov7` and install its requirements. Mount Drive for
  datasets and weights.
- Done when: `python -c "import hdr"` works locally and the notebook header cell runs
  on Colab.

### Step 1: Inspect the data and confirm conventions
- `data/inspect.py` draws boxes, both keypoints, and waypoints on 10 images per dataset.
- **Must confirm:** which keypoint is the head and which is the tail. The category says
  `['head','tail']`, but in FC_A the waypoints start at keypoint[0], and that point sits
  next to `arrow_prev`. Decide from the pictures and lock the order in `config.py`.
- Confirm what `arrow_prev` / `arrow_next` refer to: annotation `id` or `aid`.
- Done when: the overlay images clearly show correct head/tail colours.
- **Result (done):** keypoint 0 is the TAIL (at `arrow_prev`) and keypoint 1 is the HEAD
  (at `arrow_next`, where the arrowhead is drawn). This is the opposite of the category
  metadata order. `arrow_prev` / `arrow_next` hold annotation `id`s. FC_A templates 4
  and 13 have no text, by design. The order is locked in `hdr/config.py`.

### Step 2: Detection data (9 classes)
- `coco_to_yolo.py` writes YOLO txt labels.
  - Classes: arrow, connection, data, decision, process, terminator, text, arrow_head,
    arrow_tail.
  - FA classes: state, final_state, text, arrow, arrow_head, arrow_tail.
- Make `arrow_head` and `arrow_tail` boxes as squares centred on each keypoint.
  - Side ≈ 3% of the image's longer side. The paper does not give a size, so tune on val.
  - Clip boxes to image bounds.
- Write a YOLOv7 `data.yaml` per dataset: FC_A (val = FC_B val), FC_B, FA.
- Done when: re-drawing YOLO labels on images matches step 1 overlays.

### Training notebook (status: built, not yet run on GPU)
- Notebook: `notebooks/train_kaggle.ipynb`, generated by `python -m hdr.tools.build_notebook`.
- Code zip (Kaggle dataset "hdr_code"): `python -m hdr.tools.pack_code` writes `out/hdr_code.zip`.
- Runner: `hdr/tools/cloud_run.py`. It runs YOLOv7 on GPU 0 while DeepLab and then TrOCR run on GPU 1.
  It stops 20 min before the time budget and resumes from the previous run's output.
  It keeps only final weights, logs and metrics: no extra YOLOv7 epoch checkpoints, `last.pt`
  deleted once a part finishes, and only the TrOCR model with the best val CER.
- Findings while building it:
  - The FC_B offline waypoints are a rough shaft line. They miss arrowhead barbs and
    drift off the ink at corners. Masks are therefore made from real ink inside a band
    around the waypoints, plus a disc at the head, minus node interiors
    (`arrow_masks --mode ink`). The paper's plain 6 px line is still available as
    `--mode polyline`.
  - FC_A train + FC_B train = 528 mask images, the same as the paper.
  - FC_B text labels are empty, so only FC_A gives OCR text. Crops: 1739 train /
    165 val (held-out writers) / 1290 test.
  - DeepLab learning rate: the paper's lr 1e-5 only works with its 10,000 epochs. In a
    CPU check (9 epochs) loss went 0.70 → 0.65 and IoU stayed at the arrow-pixel share
    (~0.008). The Kaggle default is therefore lr 1e-4 with early stopping.
  - Mask symbol removal uses each symbol's real shape (diamond, capsule, ellipse,
    slanted parallelogram), not its bounding box. The box version erased 483 arrowheads
    that end in box corners.
  - TrOCR: keep the checkpoint's decoder start token (`</s>`). Labels are `text </s>`.
    The loss is computed in `seq_loss`, because transformers 4.57 shifts
    VisionEncoderDecoder labels twice.

### Step 3: Train YOLOv7 (Kaggle)
- Start from COCO-pretrained `yolov7.pt`.
- Settings: img 640, SGD, lr0 0.01, weight_decay 0.0005, 300 epochs (paper). On a free
  T4, batch 16 is likely; use resume checkpoints because sessions time out.
- Train one model per dataset (FC_A, FC_B, FA).
- Export `best.pt` to Drive, then copy to `weights/`.
- Done when: val mAP@0.5 is about 0.97 or higher. The paper's baseline is 97.67% on FC_A.

### Step 4: Arrow masks + DeepLabv3 (Kaggle)
- `arrow_masks.py`: for each FC_A + FC_B train image, draw arrow waypoints as polylines
  6px thick, giving a binary mask. FA has no waypoints, so the paper reuses the FC model
  for FA.
- Model: torchvision `deeplabv3_resnet50` with pretrained weights. Replace the
  classifier head with 2 classes.
- Training: resize to 700×700, Adam, lr 1e-5, cross-entropy.
- The paper says 10,000 epochs. Use early stopping on FC_B val mask IoU instead; it is
  far cheaper and fits the Kaggle time budget.
- Done when: val arrow-pixel IoU is about 0.8 or higher, and the masks look clean on
  sample images.

### Step 5: Post-processing (`postprocess.py`), local and pure Python
In order:
1. Split detections into an arrow group and a non-arrow group.
2. Non-arrows: same-class NMS with IoU > 0.50 (`GENERAL_THRESHOLD`). Keep the higher
   confidence.
3. Arrows: NMS with IoU > 0.60 (`ARROW_THRESHOLD`).
4. Arrow pairs with IoU ≤ 0.60: run connected components on the DeepLab mask inside each
   box.
   - Different component labels: keep both arrows.
   - Same component: keep the box that covers more of that component.
5. Link each arrow to its head and tail. Use the detected `arrow_head` / `arrow_tail`
   boxes that fall inside the arrow box.
   - Fallback: crop, convert to grayscale, Otsu threshold, AND with the mask, Zhang-Suen
     skeleton, then take the extreme skeleton endpoints.
   - Pick which endpoint is the head by distance to any detected head box. Otherwise use
     the endpoint whose local ink is denser (arrowhead).
6. Attach each terminator, data, process, or decision symbol to the nearest text centre.
   Text left over near an arrow becomes a branch label candidate.
- Sweep thresholds 0.30–0.80 in 0.05 steps on val, as in the paper.
- Done when: unit tests in `tests/test_postprocess.py` pass on hand-built boxes and
  masks, and val mAP goes up versus raw YOLO.

### Step 6: Text recognition (Kaggle)
- Data:
  - `text_crops.py`: FC_A ground-truth text boxes, about 1,810 crops.
  - `crohme.py`: render CROHME InkML to images, with LaTeX turned into plain operators.
  - `synth_text.py`: the 4 patterns, rendered with handwriting fonts plus augmentation.
    - `read a`, `read a, b`
    - `x = y`
    - `x = 5`
    - `x = a * b`
- Start from `microsoft/trocr-base-handwritten`.
- Train 3 configurations, as in the paper's ablation: FC_A only; + CROHME; + synthetic.
- Done when: WER and CER on the FC_A test set improve run by run, and the third config is
  best.

### Step 7: Graph build (`graph.py`)
- `Node`: id, class, bbox, text, preds, succs.
- For each arrow:
  - Tail node = the non-arrow symbol box with the highest IoU against the tail box.
  - Head node = the same test against the head box.
  - Use IoU, not distance, as the paper does. If every IoU is 0, fall back to the
    nearest box edge within a small radius.
- Decision nodes:
  - Take the 2 outgoing arrows.
  - Give each arrow the nearest yes/no or true/false label.
  - If a label is missing, use a default: down or right = No. Log a warning.
- Export the graph as JSON.
- Done when: on FC_B val ground truth fed in as "perfect detections", 100% of the graphs
  match the `arrow_prev` / `arrow_next` links.

### Step 8: Code generation (`codegen.py`)
- Start at the terminator whose text is "start". Walk the graph recursively.
- Map each node class to code:
  - data `read x`: `x = float(input())`
  - data `print/write x`: `print(x)`
  - process: an assignment statement. Split several statements on whitespace between
    `=` groups; this fixes the paper's `n=m m=r` SyntaxError.
  - decision: `if` / `else`. An edge back to a visited node becomes `while`.
  - terminator end: stop.
- Light text cleanup: normalise `×` to `*`, `÷` to `/`, `←` to `=`, and `≠` to `!=`.
- Check output with `ast.parse`. On failure, flag the line number, as in the paper.
- Done when: hand-written test graphs (sequential, if/else, loop) produce code that
  compiles and runs.

### Step 9: Pipeline + CLI
- `python -m hdr.pipeline image.png --dataset fcb --out out/`
- Writes `graph.json`, `program.py`, and `overlay.png` (boxes plus green tail / red head
  dots, like paper Fig. 7).
- Run it on the existing `test.jpeg`.

### Step 10: Evaluation (match the paper's tables)
- `det_metrics.py`: per-class AP / precision / recall at IoU 0.5 and 0.8, for raw YOLO
  and for YOLO + post-processing.
- `diagram_rec.py`: a diagram counts as recognised when all three hold:
  - Symbol count matches ground truth.
  - Every symbol has IoU ≥ 0.8 with ground truth.
  - Every arrow has the correct predecessor and successor.
- Code generation: on the paper's 6 FC_A templates (1b, 2b, 3b, 6b, 8b, 9b), report
  compile rate and functional correctness, using hand-written expected input/output per
  template.

Paper targets:

| Metric | Target |
|--------|--------|
| mAP on FC_A | 99.41 |
| AP on FC_B | 99.73 |
| Diagram recognition, FC_A | 79.5% |
| Diagram recognition, FC_B | 90.3% |
| Diagram recognition, FA | 89.2% |
| Code generation, template 2b | 84.6% |
| Code generation, 6-template average | 58.6% |

## Order and dependencies

- Steps 0–2 run locally first.
- Steps 3, 4, and 6 run on Kaggle: A on GPU 0, then B and C on GPU 1 in parallel.
- Step 5 needs weights from steps 3 and 4.
- Steps 7 and 8 can be built and tested on ground-truth annotations before any model
  exists.
- Then steps 9 and 10.

## Verification
- `pytest tests/`: post-processing, graph matching, code generation.
- The graph built from ground-truth annotations matches 100% of `arrow_prev` /
  `arrow_next` links (checks step 7 on its own).
- The evaluation scripts print tables comparable to paper Tables 4–11.
- Run end to end on `test.jpeg` and check the overlay, graph, and program by eye.

## Risks
- Head/tail keypoint order is unclear (step 1 settles it).
- Kaggle 12 h run limit: checkpoint every epoch, stop before the limit, resume from the attached output.
- CROHME is not in the repo; download it separately. Its InkML needs rendering.
- FC_A licence is CC-BY-NC-SA, so research use only.
